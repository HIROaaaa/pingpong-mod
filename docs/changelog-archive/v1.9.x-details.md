这里是从 `CHANGELOG.md` 移出来的 **v1.9.0 ~ v1.9.22** 逐条版本记录，时间都是 2026-09-21。

**为什么要归档**：动作系统（M6）与球拍建模（M9）那一天的迭代被切成了二十多个版本号，
用户 2026-09-21 拍板「改球拍和动作的版本合到一个版本，之前那些中间版本都删掉」，
于是合并成 `CHANGELOG.md` 里的单条 **v1.9.0（就地重做）**，逐条过程留在这里备查。

原样保留，未做任何改写。

## [1.9.22] - 2026-09-21（**未提交**）

**代码渲染（builtin/entity）试到底了，回退到 JSON 几何；同时把"自检截图"这套工具建起来了。**

### 为什么回退（有据可查，不是放弃）

照灾变做 `builtin/entity` + `BuiltinItemRenderer` 之后，链路的前半段全通：

```
[pingpong] 球拍几何：26 个方块，范围 x[-4.05, 4.05] y[-13.76, 0] z[-2, 2]（模型像素）
[pingpong] 球拍代码渲染被调用（这正是 builtin/entity 生效的证据）
```

也就是说：**渲染器被调用了、几何尺寸也正常**（一个小物件该有的范围）。
但屏幕上**连最简单的纯色测试方块都看不到**（我把几何换成"不采样贴图、顶点着色的纯色方块"验证过）——
所以问题在渲染时机/状态，而不在几何或 UV。继续赌这条路的性价比太低。

### 本版决定

- **球拍几何回到 JSON**（`pingpong_paddle_v4.json`：10 层拼圆 + 三明治 + 两段手柄，34 个元素）——
  这个版本此前能正常显示；
- **给它加上 `gui_light: "front"`**（灾变所有武器模型都写这行），改善 GUI 里的立体感；
- 代码渲染那套（`PaddleItemRenderer`）**保留但不注册**，注释里写明"从哪一行开始"。

### 顺带建立的开发工具：自动自检 + 截图

为了不再"改完发版让用户重启游戏看"，这一版把开发端自检做通了：

- `runClient` 会**直接进测试世界**（`--quickPlaySingleplayer`）；
- 放一个标志文件 `run/PINGPONG_AUTOCHECK` 即可开启自检：进世界后自动
  **给自己发球拍 → 切创造 → 截图到 `run/screenshots/`**（第一人称 + 第三人称各一张）；
- 开关用**绝对路径**判定（`MinecraftClient.runDirectory`）——之前试过环境变量、
  系统属性、相对路径，在 Gradle 启的 Java 进程里都不稳定。

**这套工具让本鲸娘第一次能"自己看到画面"**，本轮几次关键判断（几何正常、最简方块也不可见）
就是靠它做的 —— 之前全靠用户来回测试。

## [1.9.21] - 2026-09-21（**未提交**）

**球拍改用「代码渲染」—— 照 L_Ender's Cataclysm 的完整架构复刻。**

### 从灾变源码里学到的完整做法

用户把灾变源码放到了桌面（`new1.20.1-master`），这次看到的是**全貌**而不是猜：

| 环节 | 灾变的做法 | 本项目的对应实现 |
| --- | --- | --- |
| 物品模型 json | 只写 `parent: minecraft:builtin/entity` + `gui_light: front` + `display`，**几何是空的** | `pingpong_paddle_v5.json`（`tools/gen_paddle_entry.js` 生成） |
| 几何在哪 | Java 里 `Incinerator_Model extends AdvancedEntityModel`，构造函数里一串 `addBox(...)` | `client/PaddleItemRenderer`，用 `ModelPart.Cuboid` 在代码里拼圆盘 + 手柄 |
| 谁负责画 | `CMItemstackRenderer extends BlockEntityWithoutLevelRenderer`，按物品 switch 到对应模型 | `BuiltinItemRendererRegistry.INSTANCE.register(item, renderer)` |

**这才是"3D 武器"的正解** —— JSON 只能拼长方体，而代码想画什么画什么。

### 修掉的关键错误：贴图路径

第一版跑起来用户报"物品没有任何材质、拿在手上像空气"，本地日志里也抓到：

```
java.io.FileNotFoundException: pingpong:item/pingpong_paddle
```

原因：`RenderLayer.getEntitySolid(Identifier)` **不像模型系统那样自动补 `textures/` 前缀和 `.png`**，
必须传完整资源路径。改成 `pingpong:textures/item/pingpong_paddle.png` 后，该异常消失。

### 几何设计（代码侧）

- 拍面：**10 段拼圆**（每段半宽按圆方程取较窄边，保证不越出圆），正红 / 反黑 / 中间木芯；
- 手柄两段：握把 + 底端加宽；
- 模型空间按像素（1 像素 = 1/16 格），渲染时整体 `scale(0.0625)`；
- 复用原贴图 `textures/item/pingpong_paddle.png`。

## [1.9.20] - 2026-09-21（**未提交**）

**借鉴灾变（L_Ender's Cataclysm）的武器模型配置，修立体感；并把版本标记换成显眼品红。**

### 从灾变 jar 里扒出来的关键信息

用户提示"灾变的 3D 武器是正常的"，于是直接翻它的 jar（`L_Enders_Cataclysm-3.09.jar`）：

```json
{
  "parent": "minecraft:builtin/entity",   ← 关键 1
  "gui_light": "front",                    ← 关键 2
  "display": { "gui": { "rotation": [-90, -45, -90], "scale": [0.5, 0.5, 0.5] } }
}
```

- **`builtin/entity`**：告诉游戏"几何由代码画"。灾变 290 个物品模型里有 **44 个**这样写，
  配套的是一个自定义渲染器 `CMItemstackRenderer`（`BlockEntityWithoutLevelRenderer`）。
  → 也就是说，**本鲸娘之前试的"代码生成几何"方向没错，但挂钩用错了**
  （应该走 `BuiltinItemRendererRegistry`，而不是 `ModelLoadingPlugin`）；
- **`gui_light: "front"`**：GUI 里按"正面受光"渲染。不写这行时物品用侧向光照，
  正对我们的面偏暗、厚度方向反而亮，薄板就更像贴图 —— **这一行是立体感的关键**。

### 本版改动（走低风险部分）

1. **模型加 `"gui_light": "front"`**；
2. **display 借鉴灾变的思路**：GUI 用斜俯视 `[20, 35, 0]` + 缩放压到 0.75，
   手持缩放也整体调小（0.65 / 0.55）；
3. **版本标记换成专属品红色**：贴图图集从 32 扩到 64，第 5 格填纯亮品红
   `#FF2A8A`，标记块读这一格 —— 缩到 16×16 图标里也一眼能看见。
   用途没变：**有品红点 = 新模型生效，没有 = 还是旧资源/缓存**。

## [1.9.19] - 2026-09-21（**未提交**）

**加一个"版本标记点"，终结"到底有没有加载新模型"的争论；同时调好图标视角。**

### 用户的观察

「图标感觉就是把 3D 模型给压缩成 2D 图片了的感觉，拿在手上也是」，并附了物品栏图标：
一个 16×16 的方块，里面是红/黑/木三色分布。

### 本鲸娘的判断

物品栏图标**本来就是模型的等轴测投影**（原版机制），并不存在"把 3D 压成 2D 的图片"这一步 ——
所以图标长什么样，取决于**模型几何 + display 旋转**。之前 GUI 的旋转是纯 yaw 45°，
加上拍面本身是薄板，投影出来确实像一张三色拼图。

### 两处改动

1. **GUI 视角改成斜俯视**（`rotation [20, 35, 0]` + 缩放 0.85）：既看到正面胶皮，也能看到侧边厚度；
2. **拍面正中央加一个亮色标记点**（正反两面各一个，凸出 0.3 像素）：
   这是给"模型到底有没有生效"准备的一次性判据 —— 装上这版后，
   正反两面中央都应该出现一个明显的亮色小方块。**有 = 新模型生效；没有 = 还是旧模型/缓存**。
   比反复猜"像不像 3D"要干脆得多。

其它沿用 v4 的设定：拍面直径 10 像素（约 0.63 格）、总厚 4 像素、34 个元素、
正面红 / 反面黑 / 中间木芯、两段手柄。

## [1.9.18] - 2026-09-21（**未提交**）

球拍模型按用户反馈重做（v4：小 + 简洁 + 正反面清楚）。

用户原话：「乒乓球拍建模是正常的，而且有点太大了，只要两层能看出来正反面和手柄就行，
但是游戏里就是显示不出来这个模型，是缺少什么依赖吗」。

### 三处改动

| 项 | 之前（v3） | 现在（v4） |
| --- | --- | --- |
| 拍面直径 | 12.5 像素 | **10 像素（约 0.63 格）** |
| 总厚度 | 6.2 像素 | **4.0 像素** |
| 元素数 | 88 个 | **32 个** |
| 结构 | 16 层 + 三明治 + 外圈收边 + 5 段手柄 | 10 层拼圆 + **正反两片 + 木芯** + 2 段手柄 |
| 手持缩放 | 0.85 / 0.68 | **0.7 / 0.6**（跟着变小） |

按用户要求「只要两层能看出来正反面和手柄就行」：**正面红胶皮 / 反面黑胶皮**，
中间木芯内缩露一线木色；手柄两段（握把 + 底端加宽）。去掉了外圈收边、拍肩过渡、

### 关于"游戏里显示不出来是不是缺依赖"

**不是依赖问题** —— 物品模型是原版机制，不需要任何前置。开发环境实测：
资源重载与图集构建全程**无模型加载错误**（`Unable to load model` / `Missing model` 均未出现），
说明 JSON 本身是有效的。

如果游戏里仍看不到，按这个顺序排查最省事：

1. **换成新的模型文件名** —— v3 → v4 就是为此（文件名一变必然触发资源更新，
   排除客户端缓存）；
2. 在游戏里按 **F3 + T**（重载资源包）；
3. 确认装的是新 jar（`/pingpong diag` 看版本号）。

## [1.9.17] - 2026-09-21（**未提交**）

**球拍模型重做：回到标准 JSON 路径，几何按建模软件的思路做细。**

### 背景：用户提议用建模软件，这话点醒了我

用户原话：「就不能用类似 Blender 之类的软件做建模然后放到 mod 里吗」。
Minecraft 里对应的工具是 **Blockbench**（不是 Blender，但同样是专业建模软件），
它导出/编辑的正是我们用的**模型 JSON**。也就是说：**模型文件本来就该是"能用工具编辑的资产"**，
而本鲸娘此前一直在手写坐标拼方块 —— 把美术活当数学做，效果自然差。

### 这一版做了什么

1. **试过但放弃**：用 Fabric 的 `ModelLoadingPlugin` + 自定义 `BakedModel` 代码生成几何。
   实测 `modifyModelAfterBake` 的**回调只收到方块模型、收不到物品模型**
   （主菜单第一批是 `minecraft:block/vine`，进世界后也没有 `pingpong:item/pingpong_paddle`），
   所以那条路没生效。类保留为备选，注册调用已注释。
2. **模型 JSON 重做**（`tools/gen_paddle_model.js`，88 个元素）：
   - 拍面 **16 层**拼正圆（每层半宽 = √(R²−h²)），比之前 9 层更平滑；
   - 每层三明治：红胶皮 / 木芯（横向内缩 0.22 露出拍边木色）/ 黑胶皮；
   - 胶皮**外圈收边**（外层再窄 1.0 像素）→ 侧看有球面弧度；
   - 拍面总厚度 **6.2 像素（约 0.39 格）**；
   - 手柄 **5 段**（颈 → 握把上/下 → 底端喇叭口 → 柄底封口）+ 拍肩过渡块；
   - 保留朝向指示条。
3. **模型文件可直接用 Blockbench 编辑**：几何在
   `assets/pingpong/models/item/pingpong_paddle_v3.json`，物品名转发的
   `pingpong_paddle.json` 只写一行 parent —— 用工具改 `_v3` 即可，无需碰代码。

## [1.9.16] - 2026-09-21（**未提交**）

**球拍建模换路子：用代码直接生成几何体**（不再靠 JSON 元素拼方块）。

用户从第二轮起反复反馈"球拍还是 2D 的平面"，而之前所有尝试都是在 JSON 层面打转
（加厚 → 圆形 9 层 → 加厚到 6 像素 → 改手持角度）。JSON 元素**只能画长方体**，
圆形拍面必须拿小方块拼，边缘必然阶梯状、厚度方向做不出圆润感。

### 这一版的做法

新增两个类（走 Fabric 的渲染与模型加载 API）：

- **`client/PaddleBakedModel`** —— 自定义 `BakedModel`，用 `QuadEmitter` **逐面生成四边形**：
  - 拍面：**正 16 边形**，每个扇区是一条四边形（圆心 → 两个边缘点），边缘是平滑斜边而非阶梯；
  - 球面感：胶皮分两层，外层朝圆心收 12%，侧看有弧度；
  - 厚度：胶皮 2×(1.4+0.8) + 木芯 2.0 ≈ **5.2 像素（0.33 格）**；
  - 手柄：颈 → 握把 → 底端喇叭口，三段长方体；
  - 顶点坐标沿用模型空间 0~16 像素，**所以原来的 display（手持/掉落/GUI 旋转缩放）原封不动可用**。
- **`client/PaddleModelPlugin`** —— 用 `ModelLoadingPlugin.modifyModelAfterBake` 在烘焙完成后
  把球拍模型**包一层**：外层是我们的几何，其余（显示变换、粒子贴图、环境光、覆盖表）全部透传原模型。

### 兜底

拿不到渲染器（`RendererAccess` 为空）时自动退回原 JSON 模型 —— 不会因为渲染 API 缺失就把物品画没了。

## [1.9.15] - 2026-09-21（**未提交**）

**把几何切割改成默认关闭的开关** —— 先保证模型不被弄坏。

### 复盘：四版都没能让用户看到折弯

| 版本 | 结果 |
| --- | --- |
| 1.9.10 | `ClassNotFoundException`（字符串反射没被 remap） |
| 1.9.11 | `IllegalAccessError`（Mixin setter 写 final 字段） |
| 1.9.12 | `UnsupportedOperationException`（原列表不可变） |
| 1.9.13 | 用 `@Mutable` 终于跑通（诊断：就绪 / 已切割 2 个 / 应用 1307 次），但**看不出折弯** |
| 1.9.14 | 修坐标系后**手臂直接消失**（只剩衣服一点材质） |

每一层修完、下一层才暴露，而每次验证都要用户重启游戏配合 —— **这个投入产出比不值得继续赌**。

### 本版做法

- `ForearmPart.ENABLE_GEOMETRY_SPLIT = false`：几何切割**默认关闭**，代码与经验全部保留
  （将来有本地验证手段时，改一个 `true` 即可启用）；
- 动作仍由骨骼旋转表达（上臂大幅旋转 + 躯干转体 + 头部跟随），**至少不会把模型弄坏**；
- `/pingpong diag` 明确报告当前是"几何关节关闭"状态，避免误判为故障。

### 一句实话

1.20.1 **能做**这种弯曲（Mo' Bends 在 1.7.10 年代就做到了，方块模型机制没变）。
卡点在本鲸娘的**验证手段**：我不能本地看到画面，每次只能改完请用户重启游戏确认，
等于把试错成本转嫁给用户。所以现在的策略是**先交付不出错的东西**。

## [1.9.14] - 2026-09-21（未提交）

修坐标系的错误 —— 上一版"手臂消失"的原因。

读原方块几何时拿到的是**相对肩部枢轴**的坐标（y 大致 [-12, 0]，向下为负），
而新造的小臂部件有**它自己的枢轴**，方块坐标必须相对自己写。我把原坐标值直接填了进去，
于是小臂整体偏了半条手臂（6 像素），落到看不见的地方。

**修法**：先把坐标归一化到局部原点（`h = y - y0`，范围 [0, height]），在这个正空间里切分，
再转回各自坐标系：上臂方块 `[y0, 切点]`、小臂方块 `[-半长, 0]` 且枢轴放在肘部。

同时给 `/pingpong diag` 加了一行**真实几何数值**（"小臂几何: 原 y=[…] 切点 … 上臂装 … 小臂装 …"），
坐标类问题一眼可判，不用靠肉眼猜。

（结果：坐标修了，但折弯仍然看不出 —— 见 1.9.15 的策略调整。）

## [1.9.13] - 2026-09-21（**未提交**，按用户要求先在本地测）

**修掉第 3 个"只在真实环境暴露"的错误**：`cuboids` 不仅是 final，原列表**还是不可变的**。

三轮报错连起来看，链条一路在推进：

| 版本 | 报错 | 卡在哪 |
| --- | --- | --- |
| 1.9.10 | `ClassNotFoundException: ModelPart$Cuboid` | 类名字符串没被 remap，**没走到** |
| 1.9.11 | `IllegalAccessError: final field` | 能写入，但**写完被 JVM 拒** |
| 1.9.12 | `UnsupportedOperationException: null` | 改成 `clear()/add()`，但原列表是 `unmodifiableList` |
| 1.9.13 | — | 用 `@Mutable` accessor **整体替换**成自己的可变列表 |

### 最终解法

给 accessor 的 setter 加 **`@Mutable`**（Mixin 处理 final 字段的标准做法）：
Mixin 会生成一条绕过 final 限制的字段写入，于是可以直接把 `cuboids` 换成
`new ArrayList<>`（完全可写），不再受原列表实现的影响。

### 这三轮暴露的流程问题（比 bug 本身更值得记）

`ModelPart` 的内部结构是"final 字段 + 不可变列表"，这两条**在开发环境完全测不出来**
（Yarn 名能解析、开发环境那条路径根本没触发）。所以：

- 凡是通过反射/Accessor 触碰游戏内部结构的代码，**必须在真实产物上验证**；
- 判定"能不能写"要看三个层次：**类名是否被 remap / 字段是否 final / 容器是否可变** ——
  本鲸娘连踩三轮，正好是一轮一个。

## [1.9.12] - 2026-09-21（未提交）

**修掉第 2 个"只在真实环境暴露"的错误**：`cuboids` 是 final 字段，不能重新赋值。

用户的诊断（v1.9.11）：

```
肘关节: 不可用（IllegalAccessError: Update to non-static final field
        net.minecraft.class_630.field_3663 attempted from a different method
        (pingpong$setCuboids) than the initializer <init>）
```

这说明链条已经推进了一步（1.9.10 是 `ClassNotFoundException`，现在能走到写入这一步了），
但**写入方式错了**：`ModelPart.cuboids` 是 **final 字段**，Mixin 为 `@Accessor` 生成的 setter
在运行时被 JVM 拒绝（final 字段只能在声明处或构造器里赋值）。

### 修法：改列表内容，不重新赋值字段

```java
original.clear();          // 上臂只留上半段

## [1.9.11] - 2026-09-21

**修掉一个只在"装进游戏"时才暴露的错误**：上一版（1.9.10）的几何切割在生产环境**根本没执行**。

### 根因：字符串反射遇上 remap

上一版用 `Class.forName("net.minecraft.client.model.ModelPart$Cuboid")` 这种**字符串反射**：

- **开发环境**（`runClient`）是 **Yarn 名**，能解析 → 我本地测着"没问题"；
- **生产环境**（装进游戏）jar 里是 **intermediary 名** → `class_630$class_628`；
- 于是 `ClassNotFoundException`，切割一次都没跑过。

这是"开发能跑、装进游戏失效"的典型陷阱 —— 而本鲸娘此前所有验证都在开发环境，
**从没在真正的产物里验证过这条路径**。

### 修法（两条都用"会被重映射"的写法）

1. **类引用替代类名字符串**：`ModelPart.Cuboid.class` 交给 loom 重映射；
2. **Mixin Accessor 替代字段反射**：新增 `mixin/ModelPartAccessor`
   （`@Accessor("cuboids")` / `@Accessor("children")`）—— 访问器方法名随 remap 一起翻译，
   Yarn / intermediary 都能命中。

```

## [1.9.10] - 2026-09-21

**照 Mo' Bends 的做法重写肘关节：把上臂方块几何切成两段。**

### 参考了什么

去读了 [MoBends-Reforged](https://github.com/astryxion/MoBends-Reforged)（它支持到 1.16.5）
的源码，核心在 `BoxMutator.sliceFromBottom()`：

```
1. 记下原方块尺寸与 UV；
2. 在切点切一刀：上半段留给上臂，下半段作为小臂；
3. UV 按比例切：vSizeSlice = vSize × (newHeight / height)，
   上半段取 vPos 起、下半段取 vPos + vSizeSlice 起 → 皮肤纹理在切口处正好接上；
4. 切开后隐藏内侧的面（上臂藏 bottom、小臂藏 top），避免看到空心；
5. 小臂挂在上臂的肘部位置、相对上臂旋转 —— 这就是"胳膊折了"。
```

**关键认识**：Mo' Bends 的弯曲**根本不是顶点变形，而是几何切割**。我们前几轮走的
bendy-lib 顶点变形（用户从 40° 试到 150° 回答"全都没区别"）从一开始就是错的方向。

### 本版实现（`client/ForearmPart` 重写）

- 读原方块的真实几何（`minX/minY/minZ/maxX/maxY/maxZ`，不再硬编码 4×12×4）；
- 在 `y0 + height × 0.5` 处切成两段：上臂保留上半段、小臂是下半段；
- 小臂枢轴放在切点（相对上臂起点的一半高度）→ 绕"肘"旋转；
- 小臂挂进上臂的 `children`（私有字段，反射）；
- 若原版重建了部件结构，`SPLIT_DONE` 表里没有就会自动重新切（弱键，不阻止回收）。

### 三重确认，避免又是"看着改了其实没生效"

1. **启动探测**：`/pingpong diag` 里的"肘关节"一行报告反射是否就绪；
2. **切割日志**：第一次真正切割时打一行
   `[pingpong] 已把右臂几何切成两段：上臂 + 小臂（小臂挂在肘部，可独立旋转）`
   —— 进游戏就能在日志里看到，不用猜；
3. **诊断计数**：`肘关节: … / 已切割手臂: N 个 / 应用 M 次`。

### 开发流程改进

`runClient` 加了 `--quickPlaySingleplayer`，开发端可直接进世界（动作/模型这类改动
必须看着验证，不能再"发版让用户重启游戏试"）。

### 关于"playerAnimator 和 bendy-lib 会不会冲突"

用户提了这个问题，查过两边的 mixin 之后可以明确回答：

- **两者不冲突，是配套的** —— bendy-lib 提供顶点级变形能力，playerAnimator 是调用它的接口层；
- 但**两者会碰同一批模型部件**：playerAnimator 的 `PlayerModelMixin` 在构造时会自动
  `addBendMutator` 给各部件，而本 Mod 也会 `initBend` 一次（同一个 "bend" 名字的变形器，

- 所以真正的风险不是"互相打架"，而是**谁先谁后把对方的角度覆盖掉**。
  `/pingpong diag` 里的命中计数与 bend 调用计数就是用来把这件事定性的。

## [1.9.4] - 2026-09-21

M6/M9 第五轮。用户原话：「球拍还是3D的模型，bendy-lib这个依赖我也装了，人物还是会折，

### 修复：弯曲的真正原因 —— 漏了 `initBend`

上一版查到"没装 bendy-lib 时会静默降级"，但装上网后**还是不会弯**。反汇编
`BendHelper.bend()` 才看清它的完整链路：

```
bend(part, x, y)              → ModelPartAccessor.optionalGetCuboid(part, 0)
                              → mutableCuboid.getAndActivateMutator("bend")
                              → BendableCuboid.applyBend(x, y)
initBend(part, direction)     → mutableCuboid.registerMutator("bend", BendableCuboid.Builder…)
```

也就是说：**名为 `"bend"` 的变形器只有 `initBend()` 才会注册**，光调 `bend()` 时那个

现在流程改成：首次见到某个部件时 `initBend(part, Direction.DOWN)`（在关节处弯折），
之后每帧 `bend(part, 角度, 0)`；用弱键表记住已初始化的部件，不重复注册。

## [1.9.3] - 2026-09-21

M6 收尾 + M9 球拍建模。用户原话：「1.动作还是很僵硬的那种，没有变成平滑的弯曲
2.这次改完先把球拍的3D建模弄好，现在不好看击球效果」。

### 修复：弯曲代码其实一直没生效（重要）

playerAnimator 在**静态初始化时**检测 bendy-lib 是否加载，没装就把 bend 实现换成
`DummyBendable`（空实现）—— 所以我们调 `IBendHelper.bend()` **不报错、但什么都不会弯**。
这正是"加了弯曲代码却没效果"的原因。

- 现在先查 `dev.kosmx.playerAnim.impl.Helper.isBendEnabled()` 再决定是否调用（结果缓存，不每帧反射）；
- 检测不到时在日志里**明确写一行提示**，而不是静默失败；
- ⚠️ **想看到大臂/小臂的弯曲，必须在客户端装 [bendy-lib](https://modrinth.com/mod/bendy-lib)**
  （48KB，客户端 mod）。它是可选依赖：不装不会崩，只是不弯。

### 修复：动作僵硬（两处根因）

1. **相位是顺序切换的**：旧写法 `if (swing<0.35) 只给引拍 / 0.35~0.75 只给前挥 / 之后只给随挥`，
   每段边界上权重是**阶跃**的 —— 动作会"咔"地跳一下。
   现在改成**相邻相位 smoothstep 交叉淡入淡出**（引拍→前挥在 0…0.45 过渡、前挥→随挥在 0.55…1.0 过渡），
   任何时刻都是两段姿态按比例混合，没有阶跃点。
2. **缓动是按帧走的**：旧写法每帧走固定比例，30fps 与 240fps 的收敛速度差 8 倍。
   现在把系数解释成"每 1/20 秒收敛多少"，按**这一帧的实际时长**折算（帧长夹在 4~100ms），
   并把整体速度放缓（引拍约 0.4 秒、前挥约 0.2 秒）。

### M9：球拍模型重建（圆形拍面）

原来的球拍只有 **6 个矩形块**，拍面是长方形 —— 近看还是像块板。现在由
`tools/gen_paddle_model.js` 生成，**32 个元素**：

- **圆形拍面**：原版模型只能画长方体，做不出圆 —— 所以把拍面拆成 **9 层**，
  每层的半宽按圆方程 `w(h) = 0.5·√(d² − h²)` 算出来，叠起来就是十六边形，看着是圆拍面；
- **三明治结构**：红胶皮（0.8 厚）/ 木芯（1.4 厚，横向内缩 0.25 露出拍边木色当倒角）/ 黑胶皮；
- **尺寸按真实球拍**：拍面直径 13 像素（约 0.8 格）、柄 8 像素（约 0.5 格）；
- **手柄三段**：颈部过渡 → 主握 → 底端喇叭口，柄底封一块木头横截面；
- 保留拍面朝向指示条（任何角度都能看出拍面朝哪）。

脚本自带几何自检（坐标不越界 [-16,32]、无零尺寸面、UV 在 32×32 内），
这几条都是"模型整个不渲染/显示紫黑格"的经典原因。

### 验证

7 个套件全绿；dev 客户端启动无异常、模型与贴图加载无报错；产物自检通过。

## [1.9.2] - 2026-09-21

M6 第三轮：按实测反馈继续修。用户原话：「1.动作触发时虽然能看到动作，但是玩家的本体不动，
而是多出来一个身体执行动作 2.正反手搓球的动作现在和拉球一样，搓球动作需要改成和现实中搓球一样的
3.反手拉球手臂是从腹部往下引拍然后往上拉的 4.击球点也要相应更改，点位要跟着动画里球拍的位置更改，
不要固定在一个地方」，随后补充「也不是多出来一个身体，其实只有头和头发分离了，头发没有跟着任务动，
并且人物拉球时上半身和腿部是直接折开的，这个也需要变成和手臂一样弯曲的感觉」、
「而且手臂要有弯曲的效果，要能体现的出来大臂和小臂的那种弯曲」。

### 修复：头和头发分离（"多出来一个身体"的真因）

根因：原版 `BipedEntityModel.setAngles` 末尾会把 **hat（头发/帽层）的旋转复制自 head**，
而我们是在那之后才改 `head`，于是两层皮肤错位、头发停在原处不跟头动。
现在 `apply()` 同时接收 `hat` 并施加同一个增量。

### 修复：拉球时上半身和腿部"折开"

躯干原来只是个绕腰**刚体旋转**的方块，弯腰时上半身与腿是"折"而不是"弯"。
现在对 `body` 也用 bend（与手臂同一套机制），弯曲量跟随转体/前倾（最多 26°），腰胯间有了过渡。

### 新增：手臂在肘部弯曲（大臂/小臂的折角）

走 playerAnimator 的 `IBendHelper.bend()` —— 顶点级形变，底层是 **bendy-lib**。
弯曲量 = 基础 24° + 引拍最多 34° + 击球类型修正（搓球压直、拉球更弯），随动作缓动。
**它是可选依赖**：没装 bendy-lib 时 playerAnimator 内部是空实现，动作照常、只是不弯，不会崩
（所以不进 `depends`；想看到弯曲效果请装 bendy-lib）。

### 修复：搓球 / 拉球 / 反手拉球各有各的动作

- **搓球**：原来与拉球共用参数（用户原话「正反手搓球的动作现在和拉球一样」）。现在引拍几乎
  不往后拉、而是**压低**，前挥只往前推一点不抡，躯干略前压贴着台面 —— 像现实里搓球那样推。
- **反手拉球**：用户原话「手臂是从腹部往下引拍然后往上拉的」。正反手拉球现在分成两组参数：
  反手引拍起点更低更贴身（78° / roll −20°），前挥往上收得更陡（−78° vs 正手 −62°）。

### 修复：击球点跟着球拍实际位置走（不再固定）

新增 `util/ArmPose`：把「手型 + 击球类型 + 相位」映射成手臂姿态角度与**球拍中心相对眼睛的位置**。
客户端用它摆动画，服务端（`ModNetworking.swing`）用它定判定点 —— 两端共用同一个函数，
"看到的拍子"与"判定用的拍子"天然一致。实测判定点：待机 +0.13 格、前挥 +0.51~+0.73 格（身前）、
引拍最深 −0.73 格（身后但没出身体范围）。

### 修复：姿态状态按玩家隔离

原来的姿态目标是**全局静态变量**，联机时多个玩家会互相覆写彼此的缓动状态。
现在按 UUID 存（`PingPongModelPose.states`），退出世界时清理。

### 新增验证脚本

- `tools/paddle_point_check.js` —— 算球拍位置，断言判定点合理（在身前、能打到、不穿身体），
  并验证四类击球确实不同（搓球比拉球更靠前更低、削球更高、反手拉球与正手分开）；
- `tools/pose_direction_check.js` —— 重写为从 `ArmPose` 取参数，9 条方向/镜像/弯曲断言。

## [1.9.1] - 2026-09-21

M6 第二轮：按三条实测反馈重做动作。用户原话：「动作还是不够，现在只是手臂微微动了一下，
而且我感觉你把正反手的动作弄反了，并且我想要的效果是在蓄力拉球的时候就有手往后引拍的动作的效果」。

### 修复一：动作幅度（"只是微微动了一下"）

第一版给的角度全是 8°~30° 量级，而玩家手臂本身就有 40° 级的原版走路摆动 —— 那点增量
视觉上等于没动。现在以 **0° = 手臂自然下垂**为基准重新标定：

| 相位 | pitch | 说明 |
| --- | --- | --- |
| 持拍待机 | −30° | 手在身前、略抬，球拍举得出来 |
| 引拍（蓄满） | **+60°** | 手拉到**身后偏上**（待机→引拍整整 90°） |
| 前挥 | **−85°** | 手扫到**身前下方**（引拍→前挥 145°） |

手部实测行程：待机→引拍 11.75 像素、引拍→前挥 **12.41 像素**（约 0.78 格）。

### 修复二：正反手改成真镜像

第一版只把侧向分量乘了 ±1，俯仰方向两只手一样，所以"看着像反的、又像没区别"。
现在 `yaw / roll / bodyYaw` 都乘手型符号，且脚本断言**两支手臂的位置关于身体中线严格镜像**
（左右 x 之和 ≈ 0）。

### 新增三：蓄力阶段就有引拍动作

这是用户点出的关键缺失 —— 第一版只有挥拍那 8 tick 有动作，按住左键蓄力时手臂是静止的。
现在**蓄力进度直接驱动引拍**（用 `sqrt` 让前半程就走得明显），松手进入挥拍时从
"已经引好拍"的位置继续前挥，不做瞬间跳变。也就是：
**按住左键 = 手往后慢慢拉 → 松手 = 从后往前甩出去 → 随挥收住。**

### 新增：动作方向的自动化验证（两条脚本，都进套件）

- `tools/pose_solver.js` —— **方向求解器**。反面推：先说清"手该在哪"（待机身前、引拍身后、
  前挥身前），再反解出该给多少度。它当场抓出第一版的方向错误：引拍时手跑到了身前（z=−11.93）、
  前挥时手跑到了身后（z=+8.73）—— 也就是说**上一版把动作做反了**，幅度调多大都救不回来。
  它还暴露了模型的一条硬约束：**手臂只能绕肩旋转，手恒在过肩的竖直面内（x 动不了）**，
  所以横向扫动只能靠躯干转体给，这也正是真人打球要转腰的原因。
- `tools/pose_direction_check.js` —— 8 条方向断言（待机/引拍/前挥的语义、摆幅、镜像），
  改动作常量后必须全绿。两条脚本的常量都从 Java 源码解析，改 Java 自动跟上。

### 验证

- 8 个套件全绿（原 6 条 + 新增的这两条方向脚本）；
- dev 客户端启动无异常，Mixin 正常应用；
- 产物自检通过（版本号 1.9.1、字节码 52、库未被打包）。

### 新增：action 落到**玩家模型骨骼**上（不再只有拍子自己在飘）

之前的 `PingPongAnimations` 只对「手持物坐标系」做矩阵变换 —— 只有那把拍子在动，玩家手臂纹丝不动，
看起来像"球拍自己飘着"。现在新增 `client/PingPongModelPose` + `mixin/PlayerEntityModelMixin`：

- 注入 `BipedEntityModel.setAngles` 的 **RETURN**（不是 TAIL：这里做的是**加法**，
  若目标方法中途提前 return 会被命中两次 → 每帧叠加、几秒后手臂扭成一团；RETURN 每个出口后只加一次）；
- 用 `instanceof PlayerEntityModel` 收窄范围，僵尸/骷髅等同样用 `BipedEntityModel` 的实体不受影响；
- 四类击球（攻球/弧圈/搓球/削球）× 正反手各有自己的**躯干转体、上臂三轴旋转、头部跟随、
  非持拍手平衡摆**，拍面俯仰也会带动手臂，第三人称一眼能看出拍形；
- **平滑**靠指数缓动，且缓动速度分三段：**引拍慢（0.18）→ 触球快（0.55）→ 随挥缓（0.22）**，
  动作之间连续过渡，不再是原版那种正弦挥手；
- 本地玩家与其他玩家走同一套公式（别人的姿态从 `PaddlePoseCache` 取），所以联机时互相都看得见。

### 新增：playerAnimator 作为前置依赖

- `player-animator` 写进 `fabric.mod.json` 的 `depends`（**非** Jar-in-Jar，用户拍板玩家各自安装）。
  ⚠️ mod id 是 **`player-animator`**（带连字符），不是 `playeranimator`。
- 实测这个库的 13 个 mixin **全在 `client` 段、`mixins: []` 为空** → 纯客户端库，
  **服务端不需要装**（Modrinth 页面标的 `server_side: required` 与代码不符，以代码为准）。

  实测本机网络下 Modrinth 的 maven 端点一律 404（试过版本号加/不加 `-fabric`、URL 编码 `+`、
  以及 `maven-metadata.xml`），所以不用 maven 坐标。产物里**不会**打包它（`verify_jar` 已确认）。

### 修复：左键不再先播一次原版攻击

`MinecraftClientMixin` 原来只发通知、不取消原版逻辑，于是左键**先抡一次原版挥手**（还带攻击判定）
再进入我们的蓄力 —— 用户说的"先攻击一下"就是这个。现在手持球拍时直接 `cancel`：
不做攻击判定、不播原版挥手动画，视角照旧不动，蓄力与出球完全不受影响
（出球只依赖按键状态机，不看 `doAttack` 的返回值）。

根本看不见球」。出手点从「正上方 +0.30」改为**「眼睛 + 视线水平方向 × 0.45 格、低 0.15 格」**
