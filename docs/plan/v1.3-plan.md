## 0. 先纠正两条"上一版的理论问题"（我验证后的结论）

你说了「我前面说的理论可能有问题，你验证后也要改正」，所以先把两条要修正的放在最前面。

### 0.1 球速问题是**绝对值算错了**，不是"力度没生效"

按当前公式反推：

```
speed = clamp(0.30 + 0.85×力度 + 0.25×来球, 0.12, 1.25) × (1 + tilt×0.15)
```

用射程公式 `R = (v²·sin2θ + 2g·h·cos²θ) / g`（g = 0.030 格/tick²，球台高 h = 0.76，仰角 3°）算：

| 力度 | 出球速度 | 射程 |
| --- | --- | --- |
| 0.0 | 0.30 | **5.3 格** |
| 0.3 | 0.55 | 11.3 格 |
| 0.6 | 1.28 → 被夹到 1.25 | 19+ 格 |
| 1.0 | 1.25 | 19+ 格 |

球台全长 **2.74 格**（真实尺寸）。也就是说**哪怕轻点一下，最低档也飞 5.3 格**——
"直接打出球台"的根因是基础速度 0.30 本身就比球台长了近一倍。这只是"调小数"能解决的，
但直接报个数会让你下次还是打不上台，所以下面给完整标定表。

**目标标定（按"从近端调到对面半台"倒推）**：

| 击球方式 | 速度区间（格/tick） | 对应射程 | 说明 |
| --- | --- | --- | --- |
| 轻轻磕/挡 | 0.10 ~ 0.18 | 1.0 ~ 2.3 格 | 刚好过网、落对面近台 |
| 平击/攻球（左键，平拍） | 0.18 ~ 0.42 | 2.3 ~ 6.6 格 | 出台一点点算正常（真实攻球也常出台） |
| 搓球（右键，小力度） | 0.07 ~ 0.16 | 0.9 ~ 2.0 格 | 慢、低、贴着网过 |
| 削球（右键，蓄力 > 57%） | 0.16 ~ 0.30 | 2.0 ~ 4.4 格 | 速度中等但转速极高 |
| 拉弧圈（左键蓄满 + 摩擦） | 0.45 ~ 0.55 | 5.5 ~ 10 格（有弧线、有马格努斯下压） | 弧圈本来就该出台后急速下扎 |

关键：**"平击不能有弧线"必须靠物理保证，不能靠上限**。
平击的拍面是打开的（出射仰角 3~4°）且摩擦系数低，拉球是闭合拍面 + 向上摩擦（仰角 15~25° + 高转速），
两者由 §3 的接触模型自动区分，不需要写 if。

### 0.2 抛球高度单位搞错了

现在 `0.34 ~ 0.74 格/tick`，从眼高 1.62 起算，**峰值约 3.6 ~ 10.7 格**——
10 格高等于把球抛到树顶上，而球台只有 0.76 格高，完全不成比例。

真实发球抛球高度 ≈ 手以上 0.3~0.5 m ≈ **0.3~0.5 格**。
换算成初速度（v = √(2gh)，g = 0.030）：**0.135 ~ 0.17 格/tick**。

但游戏里太低了玩家根本来不及调拍形，所以取游戏化折中：

| 参数 | 现在 | 改为 | 峰值高度（从眼睛算） |
| --- | --- | --- | --- |
| 最短蓄力 | 0.34 | **0.20** | 约 2.3 格（比头高一点点） |
| 蓄满 | 0.74 | **0.32** | 约 3.3 格 |
| 滞空时间 | — | **13 ~ 21 tick**（0.65~1.05 s） | 够调拍形 |

## 2. 需求 4「侧旋不侧拐」的三个真 bug（已定位）

这条你报了两次，之前两次都没修对，所以我把根因写清楚。

**Bug 1：客户端在跑自己的物理，而且是**直线**物理。**
`ModNetworking.broadcastBallMotion` 只在**击球瞬间**发一次速度包；
其余 tick 客户端拿到的是原版实体追踪的 `Entity.setVelocity` 值——那是**上一 tick 的速度**，
客户端用 `tickClient` 里**不跑马格努斯**（`tickClient` 只撒粒子）。
所以：击球瞬间客户端拿到正确速度与自旋 → 接下来 20~40 tick 全是"马格努斯不可见"的直线段，
只在弹跳/反弹那一下（服务端也在那次碰撞发了包）突然改向。→ 这就是"只有击球那一下往旁边动一下"。

**修**：自旋量级 > 0.6 时降低同步间隔（每 1~2 tick 发一次当前速度），
或者干脆改成 **服务端权威 + 客户端插值预测**（`lerp` 而不是硬读），
并把 `broadcastBallMotion` 从"只在击球时发"改成"速度变化超阈值就发（限流每 2 tick）"。

**Bug 2：`spawnParticles` 之外，客户端渲染的球位置来自 `EntityTracker`，球飞得快时会被"拉直"。**
128 格追踪范围 + 1 tick 同步率是对的，但上面 Bug 1 的不一致会让插值算出折线。

**Bug 3：地面接触时自旋被过快吃掉。**
`GROUND_SPIN_DECAY = 0.85/tick` 会在 15 tick 内把自旋吃到 9%，
而侧旋球在**台面上**弹一次之后正要靠自旋产生侧拐，于是"落地那一刻拐一下就没"。
→ 台面（`Surface.TABLE`）与普通地面要分开：台面自旋衰减 0.965，地面才用 0.85。

**验收（对照组）**：满侧旋 + 0.35 格/tick 平击，从球台一端打到另一端（约 22 tick 飞行），
横向偏移应 ≥ 0.8 格；落台后继续侧拐 ≥ 0.4 格。

## 3. 旋转-击球接触模型（需求 9~22 的公共底座）

### 3.1 核心公式

设 n = 拍面法线（单位向量，指向球来的那一侧），V = 拍面中心速度（挥拍速度），
v = 来球速度，ω = 来球自旋，R = 球半径，m = 质量，I = 2/3 mR²。

```
相对速度      u   = v - V
法向分量      un  = u · n
切向分量      ut  = u - un·n
接触点滑移    s   = ut + ω × (-R·n)        ← 自旋带来的表面速度
法向冲量      Jn  = -(1 + e) · un · m      （un < 0 才接触）
切向冲量      Jt  = -min(μ|Jn|, |s| / (1/m + R²/I)) · ŝ
出球速度      v'  = v + (Jn·n + Jt) / m
出球自旋      ω'  = ω + ((-R·n) × Jt) / I
```

**关键点：一个公式同时解释了你列出的全部现象** ——

| 情形 | 为什么是这个结果 |
| --- | --- |
| 上旋球（弧圈）被平拍挡 | ω×(-Rn) 让接触点向前上滑 → 摩擦向上 → 抬升 + 自旋减小；再被马格努斯往下压 → **下网** |
| 下旋球被平拍挡 | 接触点向下滑 → 摩擦向下 → 压低 + 去旋 → **出球软、容易下网** |
| 侧旋球被平拍挡 | 接触点侧向滑 → 摩擦侧向 → **出球向侧面弹**（你要求 9 的第一句） |
| 强上旋削球 | un 小、切向大 → Jn 小、Jt 打滑 → 出球速度骤降但 ω' 仍在 → **飞高出台**（要求 22） |
| 弱上旋重削 | 切向摩擦吃得狠 → 球被强烈反旋 → 马格努斯向上 → **下网或飘**（要求 22） |
| 拉球有弧线 | V 有向上分量 → u 的切向分量大 → 摩擦方向斜向上 → 高转速 + 合适出球角 → **拱形轨迹**（要求 10） |
| 平击没弧线 | V 水平、拍面打开、μ 低 → 几乎无切向摩擦 → 几乎无自旋 → **直线**（要求 10） |

> 于是**远近**（V 大小）与**高低**（仰角）同时变化 —— 正是你要求 11 说的两件事。

### 3.3 击球点与动作（需求 12、13、17~21）

## 7. 多版本（1.16.5 起）路线

### 7.0 M5 现状与结论（2026-09-20 实测）

**已做**：注册动作已抽到 `util/Registrar.java`（物品 / 方块 / 实体 / 物品栏四个入口），
业务代码不再直接写 `Registry.register(Registries.X, ...)`。这是多版本移植里最容易被复制粘贴污染的一层。

**卡点（实测证据）**：本机 Gradle 缓存
（`~/.gradle/caches/modules-2/files-2.1`）里 Fabric 工具链**只有 1.20.1 那一套**
（yarn 1.20.1+build.10、fabric-api 0.92.x、loom 1.6.12）。1.16.5 需要的
`minecraft 1.16.5` + `yarn 1.16.5+build.10` + `fabric-api 0.42.x` + `loom 0.7.x`
**全部不在本地**，而本机出网受限（services.gradle.org / maven.fabricmc.net 直连被拦，
只有走 Steam++ 的 HTTPS 通道偶尔可用）。所以「真的编译出一个 1.16.5 jar」这一步
**必须有网络**，不适合在受限环境里硬做。

**建议的推进方式**（等一次可联网的窗口）：
1. 在能联网时先跑一次 `gradle --refresh-dependencies` 把 1.16.5 那套依赖拉进本地缓存；
2. 再引入 Stonecutter（单 jar 多版本，注释标记 `//? if >=1.19`）或直接开第二个 branch + 独立 build 文件；
3. Mixin 必须按版本各写一份（`Camera.update`、`HeldItemRenderer.renderItem` 在两个版本签名完全不同）。

**在此之前能继续做的（不依赖网络）**：把剩余差异也收进适配层，见 §7.2。

## 10. 本轮追加的两条细化（需求 24、25）

### 10.1 乒乓球物品不消耗（需求 24）

现状 `item/PingPongBallItem.java`：

```java
if (!player.getAbilities().creativeMode) {
    stack.decrement(1);        // ← 删掉这一行
}
```

删掉后：任何模式下一颗球都能无限发球。这与需求 5「一世界一球」不矛盾——
旧球要么被"潜行右键回收"清掉，要么 600 tick 后自己消失，场上始终只有一颗。

顺带保留 `getItemCooldownManager().set(this, 4)`（4 tick 冷却），否则狂点右键会每 tick 生成一颗球。

### 10.2 抛球纯垂直（需求 25）

**根因有两个，都要改**：

```java
// 现状（entity/PingPongBallEntity.java#toss）
TOSS_DRIFT = 0.06;                                   // ← 水平漂移，虽然小但确实在"向前"
Vec3d pos = thrower.getEyePos().add(flat.multiply(0.55));   // ← 生成点在身前 0.55 格
```

已知物理事实：抛起来再落回**原生成点**，所以只要带 0.55 格的生成偏移，
球就会在"身前 0.55 格"那条竖直线上飞——从玩家视角看就是"往前抛出去了"。

**改法**：

| 项 | 现在 | 改为 |
| --- | --- | --- |
| 水平漂移 | 0.06 | **0.0**（完全垂直） |
| 生成点 | 视线的水平前方 0.55 格 | **玩家正上方**：`eyeY + 0.35`（约等于头顶再高一点） |

**为什么要放到头顶而不是原地**：原版 `Entity#move` 会把玩家碰撞箱当墙。
球放在脚/胸前会被玩家自己挡住，一次都抛不起来——这是二期已经踩过的坑（README 第 4 节坑①）。
放到头顶上方后，水平确实在玩家正上方（水平位移 0），又不会与玩家碰撞箱相交。

**还要做两件事**：

1. **检查头顶是否被方块占住**（3 格高天花板下抛球会被卡住）：生成点若落在非空气方块里，就沿竖直方向再抬高 0.3 格重试，最多 4 次，仍不行则退回"身前 0.55 格"（保证不会连球都扔不出去）。
2. **落地判定不受影响**：`表面材质` 判定读的是球下方方块，垂直抛球落回手边时读到的还是普通地面/球台，逻辑不变。

**验收**：

- 站在空旷平地上抛球，球在竖直线上起落，落地后与玩家的水平距离 < 0.05 格；
- 抛出过程中没有任何水平位移（`physicsVelocity.x == z == 0` 全程成立，可用 `PINGPONG_TRACE=1` 看日志确认）；
- 在 2 格高的封闭空间里抛球，不出现球卡在身体里的现象。

### 11.1 为什么不能靠读代码猜

滚轮链路静态读下来是通的：`MouseMixin.onMouseScroll` → `PingPongClientState.onScroll`
→ `poseDirty = true` → `syncPose()` 发包 → 服务端广播 → `markSynced`。
所以我没有直接改代码，而是把 `PingPongClientState` **逐行搬成一份可执行的仿真**
（`tools/sim_client_state.js`，纯 Node、不参与构建、不依赖 MC），
把「进世界 → 滚轮 → 切槽位 → 切回 → 再滚轮」跑成 tick 级序列。

### 11.2 复现结果（仿真输出，未修前）

```
场景 F：滚轮与滚轮之间夹着切槽位
  第 1 轮：滚一格后 tilt=-0.500，切走切回后 tilt=-0.250   ← 丢了
  第 2 轮：同样的模式，值一直卡在切走前的存档上
```

**根因**是 `tick()` 的保存时机：

```java
if (holdingPaddle) {
    if (!poseDirty) { ...从槽位存档读回... }
    // ← 滚轮刚改过的这一 tick，值只在内存里，没有写回 POSES
} else {
    savePose(slot);   // ← 只有「手里不是球拍」时才保存
}
```

于是「滚轮 → 立刻切槽位」这一串动作里，切槽位那一 tick 的 `tick()` 走的是
`holdingPaddle == false` 分支，此时 `updateSlot()` 已经在 tick 开头调用过 `onSlotChanged()`，
**`tilt/sideTilt` 已经被旧存档覆盖**，保存下去的自然是旧值。
下一次切回球拍槽位，读到的就是这份旧存档 → 看起来就是"我改不动了"。

（顺带排除的两个"看起来很可疑"但不是原因的：① 拍形夹紧在 ±1 —— 那是设计上的上限，
到顶后同向再滚当然不动，反向能滚；② 服务端回包覆盖本地值 —— 不会，`applyPose` 只写缓存与
`markSynced`，第一人称与自己的第三人称都读本地实时值。）

### 11.3 修法（一行位置）

```java
if (holdingPaddle) {
    if (!s.poseDirty) { ...读回... }
    if (s.poseDirty) {
        savePose(slot);   // ← 新增：滚轮改过的这一 tick 就把值落进槽位存档
    }
    ...
}
```

等价思路（保留给实现时二选一）：把 `onSlotChanged()` 从 `tick()` 开头挪到 tick 末尾，
或在 `onScroll()` 里立刻把值写回当前槽位。**我倾向第一行那个写法**：
改动最小、幂等（同一份值反复写没有副作用）、且不动切槽位时的读档时序。

### 11.5 顺带留下的工具

`tools/sim_client_state.js` 以后**每次改 `PingPongClientState` 都要同步并跑一遍**
（脚本头部写了与 Java 源文件的逐项对应关系）。它是这个项目里第一个能对"客户端状态机"做
