## 2. 关于「动作优化 mod」：本鲸娘查到的实情与选型

**先说实话**：本机 Minecraft 的 mods 目录里**只有** `fabric-api` / `malilib` / `worldedit` / `litematica`
（实例 `1.21.5-Fabric_0.16.14`），**没有任何动作类 mod**。所以你是看过别人的效果、想要那种质感，
而不是本机已有可参考的实现。下面是我实查到的两条可行路线（数据来自 Modrinth API，2026-09-20）。

### 路线 A：引入动画库 `playerAnimator`

| 项 | 实查数据 |
| --- | --- |
| 项目 | [playerAnimator](https://modrinth.com/mod/playeranimator)（KosmX，MIT） |
| 下载量 | **2668 万** |
| 支持版本 | 1.16.4 ~ 1.21.7（含 **1.16.5** 与 **1.20.1**）——**同时覆盖我们的两个目标** |
| 1.20.1 版本 | `1.0.2-rc1+1.20-fabric`（beta，181 KB） |
| 依赖 | 可选依赖 [bendy-lib](https://modrinth.com/mod/bendy-lib)（MIT，**client-only**，49 KB，1.20.1 有 4.0.0）——**真正让模型"弯曲"的就是它** |
| 环境 | **client_side: required / server_side: required** |

**结论：用它可以拿到你要的"能弯曲的顺滑动作"，但代价是玩家必须装这个库。**
可以靠 **Jar-in-Jar 打包**做到"玩家只装我们的 mod"，但玩家客户端的下载体积会多 ~230 KB
（playerAnimator 181 KB + bendy-lib 49 KB）——这个量级完全可以接受，四期时我否掉它的理由是
"18 万字节的强制依赖"，现在看**这个理由站不住**（181 KB 不是问题，真正的问题是它需要服务端也装）。

### 路线 B：自写轻量骨骼（不引任何库）

自己给玩家模型加**前臂**（vanilla 只有上臂，没有肘关节，这就是"弯不了"的根本原因），
按击球类型计算一组姿态（躯干 / 头 / 上臂 / 前臂），用平滑插值过渡。
bendy-lib 做的事本质也是这个，只是它做成通用库。

- 优点：**零额外依赖**，玩家只装我们的 mod；完全按乒乓动作定制（不需要通用关键帧系统）
- 缺点：要自己写 Mixin 挂模型部件、自己做插值；只覆盖我们的动作，不能复用别人的动画

### 本鲸娘的建议

**先按路线 B 做**，理由：
1. 你要的动作只有 4 类击球 × 正反手 + 抛球 + 持拍待机，**不是通用动画系统**，自写更贴合；
2. 零依赖在多版本（M5 还要吃 1.16.5）时省掉两套库版本的适配；
3. 万一效果不够顺滑，**随时可以切路线 A**（接口留好：动作只输出一组姿态数值，渲染层换实现即可）。

**这条需要你拍板**——见 §6 的问题 ①。

## 3. 各条的实现方案

### 需求 27：顺滑动作 + 抑制原版攻击（工作量最大）

**(a) 抑制原版攻击动作**
现状：`MinecraftClientMixin` 在 `doAttack` 里只**额外**发一个蓄力通知，没有取消原版攻击 ——
所以左键先播一次原版挥臂、再进入我们的蓄力。
改法：在 `doAttack` 的 `@Inject` 里判断「主手是球拍」时 `ci.cancel()`，**只**记录蓄力开始；
同时把原版攻击的"打到方块/实体"的副作用一并去掉（手持球拍时不该有攻击判定）。

**(b) 能弯曲的顺滑动作**
- 给玩家模型注入**前臂**部件（左右各一），构成「肩 → 肘 → 手」两段臂；
- 每个动作输出一组姿态：躯干前倾/侧倾、上臂旋转、前臂弯曲角、手腕角；
- 用**关键帧 + 平滑插值**（不用原版那种正弦挥手），过渡时间随力度变化：
  引拍慢、触球快、随挥缓 —— 这是"顺滑"的关键；
- 四类击球各有自己的关键帧（沿用现有 4 套动作的语义，只是从"矩阵硬编码"改成"骨骼姿态"）。

**(c) 验收**
- 左键按住时**完全没有**原版挥臂；
- 慢放（或截图连拍）能看到手臂在肘部弯曲，而不是整条手臂绕肩旋转；
- 四个动作之间切换不突兀（引拍 → 触球 → 随挥是连续的）。

### 需求 28：抛球从"视角前面一点"出手

现状：抛球生成点已经改成"玩家正上方"（M1 需求 25 为了"纯垂直"），结果**从身体里出来了、看不见球**。
改法：生成点 = 眼睛位置 + **视线水平方向 × 0.45 格**（略低于眼高 0.15），
也就是"举在面前"；同时保留"纯垂直上抛"（水平速度仍为 0）——
注意这两件事不冲突：**生成点前移不代表要有水平速度**。
（旧代码的前移是 `视线前方 0.55 + 水平漂移 0.06`，用户嫌"向前飞"；这次只前移、不动速度。）

### 需求 29：右键蓄力 + 侧旋可见度

**(a) 右键蓄力"没做"**：现在代码里已经有 `useKey` 状态机（`PingPongClient.handleSwing`），
但你实测无效 → 说明链路某处断了。排查清单（按可能性排序）：
1. `client.options.useKey` 在右键按住时会被原版"物品使用"流程消费 → 需要 `@Inject` 到
   `MinecraftClient.doItemUse()` 或 `ClientPlayerInteractionManager.interactItem` 并 cancel；
2. `holdingBallOffhand` 判断把右键整个排除了（副手拿球时）；
3. HUD 的"下一拍"提示没出现 → 说明 `useKeyWasDown` 从未置位。
**先加一个可开关的调试输出**（`PINGPONG_TRACE=1` 时每 tick 打 `useKey.isPressed()` 与蓄力值），
用日志确认断点，再改。

**(b) 侧旋不明显**：三处一起调（都要用脚本先算再改，不手拧）：
- 侧旋轴倾角 60° → 45°（竖直分量从 0.87 降到 0.71，让"落地侧拐"更强）；
- 马格努斯系数 0.003 → 需要重新标定（提高侧向加速度）；
- 球的自旋可视化：球渲染器按自旋轴画一条**旋转痕迹/尾迹**，让"转"这件事肉眼可见。
  （现在只有速度 >1 才撒粒子，几本看不到。）

### 需求 30：撤销"不消耗" + 球静止后回收

- 需求 24（不消耗）**作废** → 恢复 `stack.decrement(1)`（但保留 4 tick 冷却）；
- 新增：球进入"完全静止"状态（`restTicks` 达标）时，**自动飞回投掷者/最后击球者的物品栏**
  （找不到人就原地消失）。需要一个"回收"动画或至少一个音效 + 粒子，否则玩家会以为球凭空没了。

### 需求 31：球拍建模——第 3 次提这条，说明前两次没解决

**前两次的做法与结果**：
- 二期：从"平面 `item/generated`"改成 vanilla `elements` 3D 模型 → 你说"还是平面"；
- 四期 M2：把拍面从 0.8 像素加厚到 2.2 像素（三明治：红胶皮/木芯/黑胶皮）→ 你**还是**说"还是 2d 平面"。

**所以要换思路**。本鲸娘查了时装工坊（FashionCrafter / 4.0 时代的物品建模）那类 mod 的做法，
共同点是：**不是用原版物品模型，而是用自定义渲染器画真实几何体**。
三个可选方案：

| 方案 | 做法 | 效果 | 代价 |
| --- | --- | --- | --- |
| **A（推荐）** | Fabric `ModelLoadingPlugin` 注册**自定义 UnbakedModel**，几何体用真正厚的板（拍面 3.0 像素）+ 木芯外露 + 手柄带握把纹路 | 物品栏/手持都是实心厚板，任意角度有体积 | 需要一个模型加载器类 + JSON 指向它 |
| B | 继续加强 vanilla `elements`：把拍面拆成"上下两片胶皮 + 中间木芯"三层实体，总厚 3.2 像素，并在四角加"边条" | 有一定体积感，但仍是盒子拼的 | 纯 JSON，零代码 |
| C | 用实体渲染：手持时在 `HeldItemRenderer` 里画一个**自定义 3D 网格**（带圆角轮廓的椭圆拍面） | 最接近时装工坊的观感 | 代码量最大，且要与现有 Mixin 协调 |

**建议先做 B（半天见效、零风险）让你看效果**；如果还是觉得"平"，再上 A/C。
这样你不会为了一个观感问题等太久。

## 7. 第二阶段实测反馈（5 个现象）—— 已定位到根因

你报的原话：「球的二跳直接走直线了，根本体现不出来侧旋，击球点位有问题，
而且击球之后球会向人物的左边偏移一下再出去，不是在原位置往前出去，
并且球拍左偏还是右偏球都是这种效果出去，而且球被击中后上升的高度有点高了，也是先写计划先别开始写代码」

**已写诊断脚本**：`tools/ball_trajectory_diag.js`（跑多跳轨迹、把自旋按"上旋/侧旋/沿速度"分解）。

### 现象 A：击球后球会向"人物的左边"偏移一下再出去

**根因（已定位，代码级）**：`PingPongBallEntity.hitByPaddle` 结尾有这么一段：

```java
if (this.getPos().squaredDistanceTo(player.getEyePos()) < 2.25) {   // 1.5 格以内
    this.refreshPositionAndAngles(paddlePos.x, paddlePos.y, paddlePos.z, ...);  // ← 瞬移到拍面点
```

只要球离眼睛不到 **1.5 格**（乒乓球几乎总是这么近），球就被**瞬移**到"拍面点"。
而拍面点固定偏移是：
- 前方 `FORWARD = 0.55`（朝球台）
- 侧向 `SIDE_OUT = 0.38 × sideSign`，而 `sideSign = 正手 ? +1 : −1`
- 高度 `PADDLE_HEIGHT = 0.45`

**"往左"就是这里的侧向分量**：`side = up × outward` 指向**玩家右手**，
正手 `+0.38` 落在右手边；反手 `−0.38` 落在左手边 —— 而用户看到的始终是"往左"，
说明**实际生效的是反手那一支，或者手型没传对**（见现象 B）。

**修法**：击球后**不要瞬移**。改成"沿出球方向推出 0.15 格 + 把球抬到拍面高度"，
保留球原来的水平位置 —— 这样视觉上就是"原地被打飞"，不再横移。

### 现象 B：球拍左偏/右偏，球都是同一种效果出去

**根因**：`sideTilt`（Alt+滚轮）本该同时影响**出球方向**与**自旋**，但 M3 换成接触模型后，
`sideTilt` 只被喂进了 `stroke.worldSwing(basis, sideDegrees)` 的**挥拍方向**，
而挥拍方向的侧向偏转会被接触模型的"切向摩擦"吸收成**自旋**，
于是**出球方向几乎不变**（侧向偏转被摩擦吃掉了）。

**修法**：把 `sideTilt` 拆成两部分 ——
① 一小部分作为**出球方向的偏转**（直接旋转出球速度的水平方向，需求原话"球拍左右偏斜"）；
② 一大部分仍作为挥拍方向的偏转（产生自旋）。
另外要核对 `PlayerHand` 是否真的按 C 键切换（`state.hand` 与 HUD 是否一致）。

### 现象 C：侧旋"根本体现不出来"，二跳走直线

**实测数据**（`node tools/ball_trajectory_diag.js 4.0 0`，侧旋 4 rad/tick）：

| tick | x | 横向 z | 说明 |
| --- | --- | --- | --- |
| 4 | 1.32 | **−0.029** | 飞行中开始侧弯 |
| 8 | 2.54 | **−0.105** | 第一跳前，横向 0.105 格 |
| 12 | 3.29 | **+0.179** | 跳后侧拐换向（自旋方向决定） |
| 20 | 4.66 | **+0.626** | 第二跳前，横向 0.63 格 |

**结论：横向位移是存在的**（0.1 → 0.6 格），但**为什么你看不出来**，有两个真原因：

1. **曲线太"晚"**：第一跳前只有 0.105 格（不到 1 个球径），玩家盯着球看第一段基本看不出弯；
   真正明显（0.6 格）发生在**第二跳之后**，而那时球已经飞出台面、视角里球变小了。
2. **球没有任何"转"的可视反馈**：现在只有自旋模长 > 1 才撒 `CRIT` 粒子，
   而且粒子不带方向 —— 看不出是侧旋还是上旋。

**修法（三处一起）**：
- **提高侧旋的有效性**：`SIDE_AXIS_TILT_DEGREES` 60° → **45°**（竖直分量增大，飞行侧弯更强），
  并把 `MAGNUS_COEFFICIENT` 0.003 重新标定（用 `contact_model_check.js` 的目标：满侧旋第一跳前
  横向 ≥ 0.25 格）；
- **降低自旋衰减**：`SPIN_DECAY` 0.988 → 0.995（30 tick 后自旋保留率从 70% 提到 86%），
  让"第二段也在弯"；
- **加旋转尾迹**：球渲染器按自旋轴画一条**示踪轨迹**（3~5 个残影点，颜色区分上旋/侧旋），
  让"转"这件事肉眼可见 —— 这比继续加大物理数值更有效。

### 现象 D：球被击中后上升高度有点高

**根因**：`PADDLE_HEIGHT = 0.45`（击球点在眼睛上方 0.45 格）+ 接触模型给出的出射仰角。
实测（`contact_model_check.js`）平击 + 力度 0.5 的弧顶是 **1.21 格**（击球点 0.99），
也就是**只比击球点高 0.22 格** —— 单纯看数字不算高。
但你的体感是"高"，所以**先查两件事**：
1. 是不是 `clampElevation` 在来球带自旋时把仰角**抬到了窗口上限**（`LAUNCH_BASE_SLOW = 30°` 偏高）；
2. 是不是"瞬移到拍面点"（现象 A）把球抬到了 `eyeY + 0.45`，接着又以上抛角度飞出去，
   叠加起来显得高。

**修法**：先修现象 A（不再瞬移），再把 `LAUNCH_BASE_SLOW_DEGREES` 30° → 24°，
用 `contact_model_check.js` 复验"落点仍在对方台面内"。

### 现象 E：击球点位有问题（与现象 A 同源）

"击球点位"这个说法在代码里有**两个**含义，都要核：
1. **判定用的击球点**（`TableGeometry.paddlePoint`）：M3 已经改成"引拍驱动圆弧 + 台内伸手"，
   但**服务端判定的那个点**与**客户端画出来的拍面位置**是否一致？
   （第三人称看到拍子在哪 ≠ 服务端认为的击球点在哪 → 玩家会觉得"明明够到了却没打到"）
2. **瞬移的目标点**（现象 A）：它是拍面点，所以"球被吸到拍子位置"也是它造成的。

**修法**：先做一次"可视化对齐" —— 用 `PINGPONG_TRACE=1` 把服务端判定点与球的实际命中位置打进日志，
与渲染的拍面位置对照；确认对齐后再改数值。
